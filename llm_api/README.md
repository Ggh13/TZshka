## Эндпоинты для взаимодействия с LLM_API

### 1. **Загрузка ТЗ в виде сплошного текста**

**POST** `llm/text`

**Request:**
```json
{
  "mode": "Instant" | "Thinking",
  "standard": "ГОСТ-19" | "ГОСТ-34" | null,
  "text": "some_text"
}
```
- `mode` - режим раздумья,
- `standard` - стандарт написания ТЗ,
- `text` - текст технического задания.

**Response**

```json
{
  "success": true,
  "code": 200,
  "data": {
    "rules_checker": {
      "status": "valid",
      "issues": [
        {
          "rule_id": "...",
          "problem": "...",
          "explanation": "..."
        }
      ],
      "feedback": "..."
    },
    "standard_checker": {
      "status": "issues_found",
      "issues": [
        {
          "rule_id": "...",
          "problem": "...",
          "explanation": "..."
        }
      ],
      "feedback": "..."
    }
  },
  "error": null
}
```
- **success** — `boolean`  
  Флаг успешности запроса.  
  - `true` — запрос обработан успешно  
  - `false` — произошла ошибка.

- **code** — `integer`  
  HTTP-код ответа сервера.

- **data** — `object | null`  
  Полезные данные ответа. Присутствует только при `success = true`.

  - **rules_checker** — `object`
  
    Результат базовой проверки ТЗ
  
    - **status** — `string`  
  Результат проверки технического задания.  
  Возможные значения:  
      - `valid` — нарушений не найдено  
      - `issues_found` — обнаружены проблемы.
    
    - **issues** — `array<object>`  
  Список найденных проблем. Пустой массив, если нарушений нет.

      **Поля элемента массива:**

      - **rule_id** — `string`  
        Идентификатор правила, которое было нарушено.

      - **problem** — `string`  
        Название нарушенного правила.

      - **explanation** — `string`  
        Подробное объяснение причины проблемы.
  
    - **feedback** — `string`  
    Общая объективная оценка технического задания, сгенерированная LLM.

  - **standard_checker** - `object | null`  
    
    Результат проверки по стандарту (ГОСТ и т.д.)

    - `null` - если стандарт не передан
    - иначе структура аналогична `rules_checker`


- **error** — `object | null`
    
  Информация об ошибке. Для успешного ответа всегда `null`.
  
  **Поля объекта `error`:**
  - **type** - тип ошибки
  - **message** - описание ошибки

## Правила написания ТЗ
---------------------------------------------------------------------
РАЗДЕЛ 1. ЦЕЛИ ПРОЕКТА
---------------------------------------------------------------------

R1. Цели должны быть явно сформулированы.

R2. Цели должны быть конкретными и измеримыми (SMART).

R3. Цели не должны подменяться техническими задачами.

R4. Между целями и задачами должна быть логическая связь.

R5. Цели должны иметь метрики и сроки.

R6. Цели не должны противоречить друг другу.

R7. Цели должны быть согласованы с бизнесом.

---------------------------------------------------------------------
РАЗДЕЛ 2. ОПИСАНИЕ ЗАДАЧ
---------------------------------------------------------------------

R8. Каждая задача должна описывать: кто делает, что делает, где и зачем.

R9. Задачи должны включать сценарии использования (use cases).

R10. Границы задач должны быть явно определены.

R11. Уровень детализации задач должен быть одинаковым по всему документу.

R12. Задачи не должны быть перегружены техническими деталями.

R13. Для задач должны быть указаны приоритеты.

R14. Задачи должны учитывать текущие бизнес‑процессы.

R15. Для задач должны быть указаны источники данных.

R16. Сложные задачи должны быть декомпозированы на более мелкие.

---------------------------------------------------------------------
РАЗДЕЛ 3. ТРЕБОВАНИЯ
---------------------------------------------------------------------

R17. Требования должны быть полными и не пропускать важные аспекты.

R18. Требования должны описывать структуру и источники данных.

R19. Требования не должны противоречить друг другу.

R20. Требования должны быть связаны с целями и задачами.

R21. Требования должны быть структурированы по категориям.

R22. Требования должны содержать требования к качеству реализации.

Категории требований:
- функциональные
- нефункциональные
- требования к данным
- интерфейсные
- интеграционные

---------------------------------------------------------------------
РАЗДЕЛ 4. ДУБЛИРОВАНИЕ И КОНФЛИКТЫ
---------------------------------------------------------------------

R23. Требования не должны дублироваться.

R24. Требования не должны быть взаимоисключающими.

R25. В документе должна существовать процедура разрешения конфликтов требований.

R26. Не должно быть скрытого дублирования функциональности.

R27. Бизнес‑требования и технические требования должны быть разделены.

---------------------------------------------------------------------
РАЗДЕЛ 5. ТЕХНОЛОГИИ И АРХИТЕКТУРА
---------------------------------------------------------------------

R28. Архитектура должна следовать из бизнес‑задач.

R29. Технические детали не должны перегружать документ.

R30. Архитектурные решения не должны задаваться без анализа требований.

R31. Используемые технологии должны быть обоснованы.

R32. Технические решения должны быть связаны с бизнес‑целями.

R33. Не следует жестко фиксировать конкретные технологии без необходимости.

---------------------------------------------------------------------
РАЗДЕЛ 6. НЕФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ
---------------------------------------------------------------------

R34. Должны быть указаны требования к производительности.

R35. Должны быть указаны требования к доступности и отказоустойчивости.

R36. Должны быть указаны требования к безопасности.

R37. Должны быть указаны требования к масштабируемости.

R38. Должны быть указаны требования к сопровождению и мониторингу.

R39. Должны быть указаны требования к UX/UI.

---------------------------------------------------------------------
РАЗДЕЛ 7. ОГРАНИЧЕНИЯ И РИСКИ
---------------------------------------------------------------------

R40. В документе должен быть список технических ограничений.

R41. Должны быть описаны ресурсные ограничения.

R42. Должны быть учтены регуляторные ограничения.

R43. Должны быть описаны организационные риски.

R44. Должна присутствовать карта рисков проекта.

R45. Должны быть указаны способы обхода известных ограничений.

---------------------------------------------------------------------
РАЗДЕЛ 8. ЗАИНТЕРЕСОВАННЫЕ СТОРОНЫ
---------------------------------------------------------------------

R46. Все заинтересованные стороны должны быть идентифицированы.

R47. Требования разных ролей пользователей должны быть учтены.

R48. Ключевые пользователи должны участвовать в ранних этапах.

R49. Должна быть определена структура принятия решений.

R50. Должна существовать единая коммуникационная среда.

R51. Ожидания сторон должны быть согласованы.

---------------------------------------------------------------------
РАЗДЕЛ 9. КРИТЕРИИ ПРИЕМКИ
---------------------------------------------------------------------

R52. Должны быть определены критерии успешности проекта.

R53. Требования должны быть измеримыми.

R54. Для требований должны быть определены методы проверки.

R55. Должен быть описан процесс пользовательского тестирования (UAT).

R56. Должны быть предусмотрены акты приемки.

R57. Требования должны быть связаны со сценариями тестирования.

---------------------------------------------------------------------
РАЗДЕЛ 10. ВЕРСИОНИРОВАНИЕ
---------------------------------------------------------------------

R58. Документ должен иметь версию и дату.

R59. Должен вестись журнал изменений.

R60. Должна существовать процедура управления изменениями.

R61. Черновики и утвержденные версии должны быть разделены.

R62. Должен существовать единый источник актуальной версии.

R63. Каждое изменение должно анализироваться на влияние.

---------------------------------------------------------------------
РАЗДЕЛ 11. ЦЕЛОСТНОСТЬ ДОКУМЕНТА
---------------------------------------------------------------------

R64. Документ должен иметь единый стиль и терминологию.

R65. Разделы документа должны быть логически связаны.

R66. Каждое требование должно иметь бизнес‑контекст.

R67. Не должно быть копирования нерелевантных шаблонов.

R68. Формулировки должны быть однозначными.

R69. Документ должен проходить финальную редактуру.
